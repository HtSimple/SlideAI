# SlideAI 需求分析

> 文档版本：1.0  
> 编写日期：2026-09-28  
> 依据文档：项目说明.md  
> 文档用途：作为 SlideAI 首期产品实现、范围管理和验收的需求基线。

## 1. 项目概述

### 1.1 项目定位

SlideAI 是面向技术汇报、行业分析和企业方案等场景的演示文稿内容生成与优化系统。用户提交主题、受众、页数、风格等要求，可附上参考资料。系统通过需求解析、结构规划、知识检索、逐页写作、质量评估和定向修订，生成结构化 Markdown 演示文稿内容。

系统重点解决长内容生成中的规划、资料利用、质量检查和反复修改问题。系统生成的是可继续编辑的演示文稿文案，不负责首期的视觉排版或 PPTX 文件制作。

### 1.2 目标用户

| 用户 | 主要目标 | 典型操作 |
| --- | --- | --- |
| 内容创作者 | 更快完成有结构、有资料依据的演示文稿内容 | 填写要求、上传材料、检查大纲、修改结果、导出 Markdown |
| 系统维护者 | 配置和维护模型及运行环境 | 配置模型服务、查看运行日志、维护部署环境 |

首期重点服务内容创作者。系统维护者的高级运营、组织管理和权限管理能力不属于首期核心范围。

### 1.3 用户问题

当前演示文稿内容通常需要人工完成资料搜集、结构设计、逐页写作和多轮检查。直接让大语言模型一次性生成，容易出现结构松散、内容重复、资料利用不足和质量难以判断等问题。SlideAI 通过有状态的工作流和评测返工机制，将这些步骤组织成可检查、可修改的过程。

## 2. 需求来源与约定

### 2.1 标记说明

- **明确要求**：项目说明.md 已直接提出的能力或边界。
- **落地建议**：为使需求可实现、可操作、可验收而补充的建议；需在正式实现前确认具体取值。
- **待确认**：项目说明尚未定义，本文先记录为决策项，不假定为已确定事实。

### 2.2 优先级说明

- **P2**：后续增强能力，当前不作为首期验收阻塞项。

## 3. 产品目标与成功标准

### 3.1 产品目标

1. 用户能够通过 Web 界面提交演示文稿需求。
2. 系统能够解析需求并规划章节、子主题和页数分配。
3. 系统能够使用用户上传的资料为内容生成提供检索依据。
4. 系统能够按指定页数生成逐页内容，并以 Markdown 形式交付。
5. 系统能够评估内容质量；评估不通过时自动修订并重新评估。
6. 用户能够补充修改意见、审核结果，并在自动优化达到上限时继续控制生成过程。
7. 系统能够根据任务复杂度和用户选择，为各 Agent 调用合适的模型，并在首选模型发生可恢复故障时使用配置的备用模型。
8. 系统能够记录每次模型 API 调用的 Token 用量，并按生成任务汇总输入、输出和总 Token 消耗。

### 3.2 首期成功标准

以下是建议的首期验收结果：

- 从填写需求到得到 Markdown 的主要路径能够完整运行。
- 生成结果页数符合用户要求，每页具有标题和核心内容。
- 用户上传的支持格式文件能够进入解析和检索流程；解析失败时能看到具体文件及原因。
- 评估结果能够说明评分、问题和修改建议。
- 未通过的结果能够进入有限次数的自动修订；达到上限后能够交由用户处理。
- 系统能根据任务复杂度自动选择模型，允许用户在生成前指定首选模型，并在可恢复故障时按配置降级。
- 每个任务都能查询完整的 Token 消耗汇总，并可追溯到具体调用、节点、模型及重试/降级尝试。
- 用户可以将结果复制或下载为 Markdown 文件。

本项目说明未给出响应时间、准确率或通过分数等定量指标。相关指标在第 13 节列为待确认项。

## 4. 范围定义

### 4.1 首期范围

首期包含：

- 演示文稿需求录入和结构化解析；
- 任务创建时上传参考资料；同一批资料同时用于大纲规划和内容生成；
- 按任务难度自动选择模型、生成前手动选择首选模型，以及模型请求失败后的自动降级；
- 在大纲页面和内容工作台提供上下文聊天助手，支持用户以自然语言讨论并修改内容；
- 大纲规划及页面分配；
- PDF、Markdown、TXT、Word 资料上传和解析；
- 基于上传资料的向量检索增强生成；
- 逐页内容生成；
- 内容质量评估；
- 自动修订和重新评估；
- 用户反馈、审核和局部重生成；
- Markdown 结果预览、复制或下载；
- 模型 API 调用级 Token 计量和任务级 Token 汇总；
- FastAPI 服务、Vue 3 前端及 Docker 部署基础。

### 4.2 首期不包含

以下能力未在项目说明中列为首期目标，暂不纳入首期验收：

- 直接生成或编辑 PPTX 文件；
- 幻灯片视觉设计、模板套用和图表排版；
- 未经用户提供资料的互联网实时搜索；
- 多人实时协作、组织空间、计费或复杂权限管理；
- 对生成内容事实正确性作绝对保证；
- 用户自建、管理多个长期共享知识库。

后续如需加入，应另行定义范围及验收标准。

## 5. 典型用户场景

### 5.1 根据参考资料生成演示文稿

1. 用户输入主题、页数、使用场景、目标受众、风格和特殊限制。
2. 用户在同一任务创建阶段上传参考行业报告；系统解析文件，反馈无法识别或无法解析的输入。
3. Requirement Agent 形成结构化需求；Planner Agent 结合需求和上传资料生成大纲及页数分配。
4. 用户直接编辑大纲，或通过大纲聊天助手提出修改，确认后进入内容生成。
5. Research Agent 按大纲和页面目标从同一任务的上传资料中检索依据；Writer Agent 据此生成逐页文案。
6. 用户在内容工作台直接编辑页面内容，或通过内容聊天助手定向修改并确认正文。
7. Evaluator Agent 和 Refiner Agent 在后台自主完成质量检查、有限自动修订和重新评估；它们不是用户流程中的独立步骤或页面。
8. 用户确认当前内容后进入最终结果页，预览、复制或下载 Markdown 文档。

### 5.2 在内容生成阶段通过聊天助手修改正文

用户在内容工作台通过聊天助手提出“第三章减少技术细节，增加商业应用案例”等要求。系统以当前演示文稿及目标章节、页面为上下文，定向修订正文，展示修改结果并在后台自主重新评估；未涉及的页面应保持不变。用户确认正文后才进入最终结果与 Markdown 下载页。

### 5.3 自动修订达到上限

系统达到配置的最大自动修订次数仍未通过评估时，应停止自动循环，向用户展示当前内容、评估结果和修改建议，并允许用户接受、补充意见或指定重生成范围。

### 5.4 在大纲阶段通过聊天助手调整结构

用户在大纲页面对助手说“把第四点改成具体项目分析”。助手结合当前大纲确定目标条目，更新其标题或内容并展示修改结果。如果该条目已经对应生成页面，系统应列出受影响页面并询问用户是否重新生成，避免大纲与现有正文不一致。

### 5.5 根据任务难度选择模型并在故障时降级

用户可以在生成前选择自动模式或指定首选模型。首期模型目录包含 DeepSeek Flash、DeepSeek Pro、GLM-4.7-Flash 和 GLM-5.3-Flash。自动模式根据任务页数、专业程度、资料规模和限制复杂度选择模型；若首选模型请求超时或服务暂不可用，系统按外部配置的备用顺序切换到兼容模型，并告知用户本次实际使用的模型。显示名称、API 模型 ID、节点映射和备用顺序均由非敏感配置维护，不写死在工作流中。

### 5.6 查看单个任务的 Token 消耗

用户在任务详情或模型调用记录中查看当前任务累计的输入 Token、输出 Token、缓存 Token、推理 Token（供应商返回时）和总 Token。汇总包含需求解析、大纲生成、内容生成、后台质量评估、自动修订及聊天修改产生的全部实际调用，也包含重试和降级调用；用户可以继续查看每次调用所属节点、模型和用量明细。

## 6. 功能需求

### 6.1 需求录入与解析

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-REQ-01 | P0 | 用户可以填写主题、目标页数、使用场景、目标受众、内容风格和特殊限制。主题为必填项；其余字段按产品配置为必填或选填。 |
| FR-REQ-02 | P0 | 系统应将原始输入解析为结构化需求，至少包含主题、页数、受众和风格，并保留场景、限制及用户原文。 |
| FR-REQ-03 | P1 | 对缺失、冲突或无法理解的关键条件，系统应标明问题并允许用户补充或修正，不应悄悄将推测值当作用户要求。 |
| FR-REQ-04 | P1 | 用户可以在正式生成前查看并修改结构化需求。 |
| FR-REQ-05 | P0 | 用户应在需求录入阶段上传本任务的参考文件；文件解析结果必须同时可供大纲生成和后续内容生成使用，不得要求用户在两个阶段重复上传。 |

结构化需求建议至少包含：主题、目标页数、场景、受众、风格、特殊限制、语言、资料使用偏好和原始描述。语言、资料使用偏好属于落地建议。

### 6.2 大纲规划

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-OUT-01 | P0 | Planner Agent 根据结构化需求及当前任务已解析的上传资料生成包含章节、子主题和页面分配的大纲；使用资料时应保留可追溯来源。 |
| FR-OUT-02 | P0 | 页面分配之和必须与用户要求页数一致；若无法合理分配，系统应调整大纲或提示用户，而非静默改变页数。 |
| FR-OUT-03 | P1 | 用户可以查看并编辑大纲，确认后再生成全部页面内容。 |
| FR-OUT-04 | P1 | 大纲应体现目标受众、使用场景、风格和特殊限制。 |
| FR-OUT-05 | P0 | 用户可以在大纲页面通过聊天助手提出修改要求；助手应把清晰、指向明确的要求应用到对应大纲条目，并展示更新后的大纲。 |

### 6.3 资料上传、解析与检索

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-RAG-01 | P0 | 用户可以上传 PDF、Markdown、TXT 和 Word 文档作为本次生成的参考资料。 |
| FR-RAG-02 | P0 | 系统应校验文件格式，并对文件进行文本解析、切分、向量化和索引。 |
| FR-RAG-03 | P0 | Research Agent 应根据主题、大纲和页面内容需要，从已上传资料中检索相关文本，并将检索结果提供给 Writer Agent。 |
| FR-RAG-04 | P0 | 系统应显示各文件的处理状态；文件解析失败时应显示可理解的错误原因，并允许用户移除文件或重新上传。 |
| FR-RAG-05 | P1 | 检索片段应保留来源文件信息；在解析能力允许时保留页码或章节信息。 |
| FR-RAG-06 | P1 | 生成内容应能标示引用或资料依据，使用户可以识别内容与来源资料的关系。 |
| FR-RAG-07 | P0 | 大纲生成和内容生成必须使用同一任务范围内的文件索引。大纲阶段按主题和结构目标检索，内容阶段按章节及页面目标再次检索，不得跨任务引用资料。 |

PDF 页码、Word 段落或标题等定位方式可能因解析库而异，应在实现方案中明确。引用展示格式属于待确认项。

### 6.4 页面内容生成

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-WR-01 | P0 | Writer Agent 应依据需求、大纲和检索结果生成每页内容。 |
| FR-WR-02 | P0 | 每页至少包含页码、标题和核心要点；可以包含讲解说明或演讲备注。 |
| FR-WR-03 | P0 | 生成页数应与目标页数一致，页码连续，不应出现空白页或重复页面。 |
| FR-WR-04 | P0 | 内容应遵守目标受众、风格及用户提出的限制。 |
| FR-WR-05 | P1 | 对缺少资料支撑的判断或事实，系统应避免伪造来源；可将不确定内容标记为待核实。 |
| FR-WR-06 | P1 | 用户可以指定页面或章节进行重生成，并尽可能保留未指定部分。 |
| FR-WR-07 | P0 | 内容生成完成后，用户可以在内容工作台直接编辑页面标题、要点和备注，保存后更新当前任务版本；最终结果页只展示用户确认后的版本。 |

### 6.5 质量评估

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-EVA-01 | P0 | Evaluator Agent 应检查完整性、逻辑性、内容质量和用户需求符合度。 |
| FR-EVA-02 | P0 | 评估结果应包含总分、是否通过、问题列表和修改建议。 |
| FR-EVA-03 | P1 | 系统应检查明确的硬性条件，包括页数、必需章节或主题覆盖要求。 |
| FR-EVA-04 | P1 | 系统应持久化评估结果并用于自动修订和诊断；前端可在内容工作台显示简要后台优化状态，但评估不得成为用户必须查看或确认的流程步骤。 |

通过分数、分项权重和硬性条件的规则尚未在项目说明中定义，应采用可配置规则，并在开发前确定首期默认值。

### 6.6 自动优化与流程控制

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-LOOP-01 | P0 | 评估通过时，工作流保留当前内容并进入等待正文确认状态；只有用户确认正文后才生成最终 Markdown。 |
| FR-LOOP-02 | P0 | 评估未通过时，Refiner Agent 应根据当前内容、问题和建议生成修订版本。 |
| FR-LOOP-03 | P0 | 修订后应重新评估；工作流应避免无限循环，并记录修订次数。 |
| FR-LOOP-04 | P0 | 达到最大修订次数仍未通过时，系统应停止后台循环并在内容工作台提示用户继续直接编辑、聊天修改、局部重生成或确认当前内容，不得跳转到独立质量检查步骤。 |
| FR-LOOP-05 | P1 | Supervisor 应根据当前状态选择下一节点，并记录节点结果、评估结果和修订历史。 |

### 6.7 内容确认与人工反馈

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-HITL-01 | P0 | 用户可以在内容工作台确认当前正文、提交修改建议或指定重新生成范围；确认后才进入最终结果与 Markdown 下载页。 |
| FR-HITL-02 | P0 | 用户反馈应被写入工作流状态，并在恢复执行时提供给相关 Agent。 |
| FR-HITL-03 | P1 | 工作流暂停后应能够基于保存的状态恢复，避免从头重复解析和生成。 |
| FR-HITL-04 | P1 | 用户提交的反馈应作用于指定章节或页面；未指定范围时系统应先说明理解的修改范围。 |

### 6.8 聊天助手交互

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-CHAT-01 | P0 | 大纲页面和内容工作台均应提供聊天助手入口，助手应读取当前任务及当前展示的大纲、页面内容和内部评估结果作为对话上下文。最终结果页不承担内容修改流程。 |
| FR-CHAT-02 | P0 | 用户可以用自然语言修改大纲或内容，例如“把大纲第四点改成具体项目分析”或“第三章减少技术细节，增加商业案例”。 |
| FR-CHAT-03 | P0 | 助手应识别用户指向的章节、条目或页面；指向不明确或要求存在冲突时，应先追问，不得静默修改错误范围。 |
| FR-CHAT-04 | P0 | 修改请求必须落实到结构化大纲或页面内容及工作流状态中；助手应展示修改后的结果，而不能只返回文字建议。 |
| FR-CHAT-05 | P0 | 大纲修改影响已生成页面时，助手应列出受影响范围，并让用户选择是否重新生成相关页面；不得未经提示就重生成整份文稿。 |
| FR-CHAT-06 | P0 | 内容修改应按识别出的页面或章节定向执行，并对修改后的内容重新评估。 |
| FR-CHAT-07 | P1 | 用户选中某个大纲条目或页面后，可以将其作为明确的对话对象；助手也应能处理用户在消息中直接说明的目标范围。 |
| FR-CHAT-08 | P1 | 对话历史、目标对象、修改请求及执行结果应关联到生成任务，并在任务恢复后可查看。 |
| FR-CHAT-09 | P1 | 单一且明确的局部修改完成后，助手应展示修改摘要和结果并提供撤销或再次修改入口；影响大范围内容或改变页数等关键约束时，应先展示方案并征求用户确认。 |

推荐交互流程：用户在大纲或内容页面打开侧边聊天面板并描述修改；助手结合当前页面上下文解析目标；不明确时追问；明确后应用定向修改并显示结果。若大纲修改会影响已生成页面，先展示影响页面和重新生成选项。具体页面布局由 UI 设计阶段确定。

### 6.9 Markdown 输出与前端交互

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-UI-01 | P0 | Vue 3 前端的任务流程必须按“需求输入与文件上传 → 大纲生成、直接编辑和聊天修改 → 资料检索与内容生成、直接编辑和聊天修改 → 最终结果展示与 Markdown 下载”组织。 |

| FR-UI-10 | P1 | 任务详情应展示任务级 Token 汇总，并提供查看逐次调用用量明细的入口。 |

建议的 Markdown 结构为：文档标题、需求摘要、大纲、逐页标题与要点、说明或备注、资料引用（如启用）。具体模板待确认。

### 6.10 模型分层、自动选择与故障降级

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-MODEL-01 | P0 | 首期模型目录必须包含 DeepSeek Flash、DeepSeek Pro、GLM-4.7-Flash 和 GLM-5.3-Flash；模型提供商、实际 API 模型 ID、显示名称和能力档位不得硬编码在工作流逻辑中。 |
| FR-MODEL-02 | P0 | 自动模式应根据任务页数、领域专业程度、参考资料规模、约束数量及分析深度等因素评估任务复杂度，并选择适当档位。首次路由可使用已填写需求和文件元数据进行初步估计；需求解析后应更新复杂度，再为后续节点选模。 |
| FR-MODEL-03 | P0 | 模型路由应按任务复杂度及调用节点，为需求解析、大纲规划、页面写作、评估和返工等模型调用选择模型。具体节点映射应可配置。 |
| FR-MODEL-04 | P0 | 用户可以在生成前选择自动选模，或指定一个首选模型；手动选择时优先采用该模型，不再按自动复杂度替换首选模型。 |
| FR-MODEL-05 | P0 | 每个首选模型应支持配置备用模型及顺序。首选模型遇到超时、网络故障、限流或服务端错误等可恢复故障时，系统在有限重试后应切换到能力兼容的备用模型；备用链必须来自模型配置，不得写死。 |
| FR-MODEL-06 | P0 | 用户手动选择的模型仍可按已配置策略自动降级；降级后系统应明确告知用户实际使用的模型及降级原因。 |
| FR-MODEL-07 | P0 | 系统应按每次模型调用记录所选档位、首选模型、实际模型、调用节点、重试/降级情况和结果状态。 |
| FR-MODEL-08 | P0 | 所有备用模型均不可用时，系统应保留任务现场，指出失败节点和错误类型，并允许重试或调整模型后继续。 |
| FR-MODEL-09 | P1 | 自动选模应能说明档位选择的主要依据；任务运行中不得丢失此前已完成的节点结果。 |
| FR-MODEL-10 | P1 | 对认证、参数或输出格式等非服务暂时故障，系统应区分错误类型并给出处理提示，避免无意义地重复调用同一备用链。 |
| FR-MODEL-11 | P0 | 模型接入必须使用工厂模式：`LLMServiceFactory` 根据模型目录中的 provider 创建对应服务；工作流节点和 Model Router 只依赖统一的 `LLMService` 接口，不得直接实例化厂商 SDK。 |
| FR-MODEL-12 | P0 | service 层必须分别实现 `DeepSeekService` 和 `GLMService`，负责各自的请求参数、响应解析、错误归一化及 Token usage 提取；同一厂商的多款模型通过配置的 API 模型 ID 复用对应 service。 |
| FR-MODEL-13 | P0 | `.env` 只保存 API Key 等敏感值，首期至少包含 `DEEPSEEK_API_KEY` 与 `GLM_API_KEY`；模型名称、API 模型 ID、base URL、能力档位、超时、节点映射及备用链存放在独立的非敏感配置文件中。`.env.example` 只保留变量名和空占位符。 |

首期模型目录如下。表中 API 模型 ID 是初始配置值，运行时仍以非敏感模型配置文件为准，供应商升级模型时无需修改业务代码。

| 显示名称 | provider | 初始 API 模型 ID | 建议档位 | 适用任务 |
| --- | --- | --- | --- | --- |
| DeepSeek Flash | `deepseek` | `deepseek-flash` | 快速/经济 | 需求提取、轻量总结、简单大纲和短文稿 |
| DeepSeek Pro | `deepseek` | `deepseek-v4-pro` | 高级 | 复杂大纲、专业写作、多约束分析和高质量修订 |
| GLM-4.7-Flash | `glm` | `glm-4.7-flash` | 快速/经济 | 常规中文任务、快速结构规划和轻量内容生成 |
| GLM-5.3-Flash | `glm` | `glm-5.3-flash` | 均衡/高级 | 复杂中文内容、长上下文资料理解和多步 Agent 任务 |

用户选择的首选模型应作为整个任务的默认偏好；节点能力映射和故障降级仍使用配置策略。自动模式可以按节点选择不同档位。模型路由器应优先使用规则化特征和结构化复杂度结果，记录选择依据并提供稳定、可复现的路由行为。

建议的依赖方向为：`工作流节点 → Model Router → LLMServiceFactory → DeepSeekService / GLMService → 厂商 API`。Factory 根据模型配置的 provider 返回 service；service 接收实际 API 模型 ID，不在类内写死 Flash 或 Pro 型号。

建议的后端文件职责如下；实际根包名可按项目结构调整，但职责不得合并回工作流节点：

```text
backend/src/slideai/application/models/llm_service.py         # LLMService 接口、统一请求/响应/错误类型
backend/src/slideai/application/models/factory.py             # LLMServiceFactory，仅按 provider 创建 service
backend/src/slideai/application/models/deepseek_service.py    # DeepSeekService，支持 Flash 与 Pro
backend/src/slideai/application/models/glm_service.py         # GLMService，支持 GLM-4.7-Flash 与 GLM-5.3-Flash
backend/src/slideai/application/models/token_usage_service.py # 调用 usage 落库、幂等和任务聚合
backend/config/models.yaml                                    # 非敏感模型目录、ID、URL、超时、档位和备用链
.env                                                          # 仅 API Key 等敏感值，不提交版本库
```

### 6.11 Token 消耗记录与任务汇总

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-TOKEN-01 | P0 | 每一次实际发出的生成模型或 Embedding API 请求都必须创建调用记录，并关联任务 ID、工作流节点、调用用途、提供商、实际模型和尝试序号。 |
| FR-TOKEN-02 | P0 | 调用成功后应保存供应商返回的 `input_tokens`、`output_tokens` 和 `total_tokens`；供应商返回缓存 Token 或推理 Token 时，还应分别保存 `cached_input_tokens` 和 `reasoning_tokens`。 |
| FR-TOKEN-03 | P0 | 任务级 Token 汇总应累计该任务全部实际调用，包括需求解析、大纲生成、Embedding、内容生成、后台评估、自动修订、聊天修改、重试和降级调用，不得只统计最终成功结果。 |
| FR-TOKEN-04 | P0 | 每个重试或备用模型调用必须作为独立尝试记录，避免覆盖上一次用量；任务总量由调用明细聚合或通过同一事务安全更新。 |
| FR-TOKEN-05 | P0 | 供应商未返回 usage 或请求在 usage 产生前失败时，Token 字段应为 `null` 并记录 `usage_status=unavailable`，不得以 0 冒充已确认用量。 |
| FR-TOKEN-06 | P0 | 后端应提供 `GET /tasks/{taskId}/token-usage`，返回任务汇总、按模型汇总、按节点汇总及逐次调用明细；接口只能查询指定任务的数据。 |
| FR-TOKEN-07 | P1 | 汇总接口应返回 `usage_status` 和 `is_complete`，明确区分完整计量与存在缺失 usage 的估算不完整状态。 |
| FR-TOKEN-08 | P1 | Token 计量只记录供应商返回的实际用量，不在本需求中根据 Token 推算费用；如后续需要成本统计，应另行引入带版本和生效时间的价格配置。 |
| FR-TOKEN-09 | P0 | Token 用量写入失败不得丢失模型调用的业务结果；系统应记录计量异常并支持补偿，但不得重复累计同一 `provider_request_id` 或同一调用尝试。 |


## 7. Agent 职责与边界

| Agent / 组件 | 职责 | 主要输入 | 主要输出 |
| --- | --- | --- | --- |
| Supervisor | 编排工作流、维护状态、处理条件路由 | 当前 SlideState | 下一节点、流程状态 |
| Model Router（模型路由器） | 根据任务复杂度、用户首选和节点策略选择模型；处理受控重试和备用模型切换 | 任务状态、节点类型、用户模型偏好、模型目录 | 实际模型、路由原因、重试或降级记录 |
| LLMServiceFactory（模型服务工厂） | 根据模型配置中的 provider 返回统一模型服务实现 | provider、模型目录、密钥引用 | `DeepSeekService` 或 `GLMService` 实例 |
| DeepSeekService | 调用 DeepSeek Flash / DeepSeek Pro，归一化结果、错误及 usage | 统一调用参数、DeepSeek 模型 ID、服务端 API Key | 统一模型响应、统一错误、Token usage |
| GLMService | 调用 GLM-4.7-Flash / GLM-5.3-Flash，归一化结果、错误及 usage | 统一调用参数、GLM 模型 ID、服务端 API Key | 统一模型响应、统一错误、Token usage |
| Token Usage Recorder | 按调用尝试持久化 usage，并生成任务、模型和节点维度汇总 | 统一模型响应、调用上下文、provider request ID | 调用明细、任务 Token 汇总、计量完整性状态 |
| Requirement Agent | 提取和规范用户需求 | 用户原始输入 | 结构化需求 |
| Planner Agent | 规划章节、子主题及页数分配 | 结构化需求 | 大纲 |
| Research Agent | 检索资料并整理依据 | 需求、大纲、资料索引 | 检索片段及来源信息 |
| Writer Agent | 生成或按反馈修订页面内容 | 需求、大纲、资料、反馈 | 逐页内容 |
| Evaluator Agent | 按质量维度评估内容 | 需求、大纲、逐页内容 | 分数、通过状态、问题和建议 |
| Refiner Agent | 根据评估意见优化内容 | 当前内容、评估结果 | 修订后的内容 |
| Markdown Generator | 将结构化结果组织为 Markdown | 需求、大纲、页面、评估和来源 | 最终 Markdown |
| 对话助手（交互层） | 结合页面上下文理解修改意图、追问歧义并将明确请求路由到相应工作流节点 | 当前任务、对话消息、选中条目或页面 | 结构化修改请求、澄清问题、执行结果 |

对话助手负责把自然语言转换为有目标范围的工作流操作；具体修改仍由大纲或内容节点执行，并进入后台自主评估流程。质量评估和自动修订属于 Agent 内部闭环，不是用户必须经过的交互步骤。是否将对话助手实现为独立 Agent 属于技术设计选择。

各 Agent 应通过明确的状态字段交换结果，避免依赖不可追踪的隐式对话上下文。

## 8. 业务规则与工作流状态

### 8.1 主工作流

用户输入需求并上传文件 → 文件解析/索引与 Requirement Agent 解析需求 → 初步复杂度估计及模型选择 → Planner Agent 结合需求和资料生成大纲 → 用户直接编辑或通过聊天修改大纲并确认 → Research Agent 按页面目标检索资料 → Writer Agent 生成页面内容 → 用户直接编辑或通过聊天修改内容并确认 → 生成最终 Markdown → 最终结果展示、复制或下载 → 完成。

Evaluator Agent 与 Refiner Agent 在内容生成、直接编辑或聊天修改之后由系统自主运行，形成“评估 → 有限自动修订 → 重评”的内部闭环。该闭环可以更新内容和内部状态，但不新增用户流程页面；达到自动修订上限时，内容工作台显示可处理提示，由用户继续编辑、通过聊天修改或确认当前版本。

首次需求解析使用用户指定的首选模型；自动模式依据已填写字段和上传文件元数据进行初步选模。解析出完整需求后，系统更新复杂度，并为后续模型调用重新路由。Model Router 在每个模型调用前结合当前复杂度、任务级手动首选和节点策略选出实际模型，再由 LLMServiceFactory 创建厂商 service。模型调用发生可恢复故障时，按有限重试和备用链执行；每次实际尝试单独记录 Token usage。调用恢复后工作流从失败节点继续，不重复已完成节点。

在大纲确认和最终内容查看阶段，用户也可以通过聊天助手提交修改。助手将请求路由到大纲修改或页面修订流程；修改完成后更新当前内容，必要时重新评估。

- 评估通过：保留当前内容，等待用户在内容工作台确认。
- 评估未通过且仍可修订：后台进入 Refiner，再次生成或修订并评估，不要求用户进入评估页面。
- 评估未通过且已达修订上限：内容工作台提示用户继续修改或接受当前版本。
- 用户提出修改：保存反馈后恢复相关节点。
- 用户确认正文：生成最终 Markdown 并进入最终结果页。

### 8.2 状态字段

项目说明提出的核心 SlideState 字段为：

- user_requirement：结构化用户需求；
- outline：演示文稿大纲；
- retrieved_documents：检索到的资料片段；
- slides_content：逐页内容；
- evaluation_result：评估结果；
- revision_count：修订次数；
- human_feedback：人工反馈；
- conversation_history：聊天消息、当前对话目标及助手执行结果；
- pending_change：等待用户确认或补充信息的修改请求；
- model_preference：用户选择的自动模式或首选模型；
- task_complexity：自动模式得出的复杂度及判断依据；
- model_call_history：各节点的所选模型、实际模型、重试和降级记录；
- token_usage_summary：任务累计输入、输出、缓存、推理及总 Token，以及计量完整性状态；
- final_markdown：最终 Markdown。

落地建议补充任务标识、当前节点、任务状态、文件处理状态、错误信息、修订历史和时间信息，以支持前端展示、故障恢复和审计。

### 8.3 状态建议

任务状态建议至少包含：待处理、处理中、等待用户反馈、已完成、失败、已取消。实际状态名可以按实现统一，但前后端含义必须一致。

## 10. 外部接口与工具需求

### 10.1 后端接口职责

后端通过 FastAPI 提供前端所需能力，至少覆盖：

- 创建生成任务并提交需求；
- 获取可选模型及能力档位，并在任务创建时提交自动模式或首选模型；
- 查看任务各节点实际调用的模型及降级状态；
- 获取任务级 Token 汇总、按模型/节点汇总和逐次调用 usage 明细；
- 在任务上下文中发送聊天消息、获取澄清问题或修改结果；
- 上传、查看和移除任务资料；
- 查看任务状态、当前阶段和错误信息；
- 查看或修改大纲；
- 查看、直接编辑或通过聊天修改逐页内容，并提交正文确认或局部重生成请求；
- 获取、预览和下载最终 Markdown。

Token 汇总接口固定为 `GET /tasks/{taskId}/token-usage`。其他具体 HTTP 路径、请求字段、流式状态推送方式和鉴权策略属于技术设计阶段内容。

Token 汇总接口至少返回以下语义结构：

```json
{
  "task_id": "uuid",
  "usage_status": "complete",
  "is_complete": true,
  "totals": {
    "input_tokens": 0,
    "output_tokens": 0,
    "cached_input_tokens": 0,
    "reasoning_tokens": 0,
    "total_tokens": 0
  },
  "by_model": [],
  "by_node": [],
  "calls": []
}
```

`calls` 中每项应包含调用 ID、节点、用途、provider、实际模型、尝试序号、结果状态、usage 状态及各 Token 字段。接口不得返回 API Key、完整提示词或厂商鉴权信息。

### 10.2 Agent 工具

- Knowledge Search：在当前任务的知识索引中检索相关内容。
- Document Analyzer：解析用户上传的资料。
- Content Evaluation：执行可复用的内容检查。
- Markdown Generator：把结构化结果转换为最终文档。

Agent 对工具调用失败应能识别并将错误反馈到工作流状态，不能将工具错误伪装成成功结果。

## 11. 非功能需求

以下指标中，项目说明未明确量化值的部分均为落地建议，需结合部署环境确认。

### 11.1 易用性

- 表单字段应有清晰说明和输入校验。
- 页面应区分生成阶段、等待用户处理和最终结果。
- 用户流程中只呈现需求/文件、大纲、内容工作台和最终结果；后台评估不得要求用户额外确认才能继续正常流程。

### 11.2 可靠性

- 工作流应记录修订次数并设置最大值。
- 节点失败时应保留足以定位问题的任务状态。
- 模型调用应区分可恢复服务故障和配置/输入错误；可恢复故障按有限重试和备用链处理。
- 模型切换后应从失败节点恢复，保留已完成结果，避免用户重复提交整个任务。
- 对可重试的模型或检索错误，应允许用户重试或恢复任务。
- 长任务应支持状态查询；若要求用户中断后继续，需实现持久化检查点。
- Token usage 记录必须具备调用级幂等标识，重试计入新尝试，同一次尝试不得重复累计。

### 11.3 安全与隐私

- 上传文件类型和大小应由服务端校验，不能只依赖浏览器校验。
- 文件内容不得被解释为系统指令；资料只作为检索上下文使用。
- `.env` 只保存 API Key 等敏感值；真实密钥不得提交版本库、返回前端或写入普通日志。模型名称、API 模型 ID、base URL、超时、档位和备用链必须保存在独立的非敏感配置中。
- 任务资料和生成内容不应在不同用户或任务间意外混用。
- 文件大小限制、保留期限、传输和存储保护要求需在部署前明确。

### 11.4 性能

- 文件解析、向量化和生成可能耗时较长，应采用可查询状态的任务流程。
- 首期应避免同步请求因长时间生成而超时。
- 单文件大小、单任务文件数、最大页数和并发任务量待根据运行环境确定。

### 11.5 可维护性

- Agent 节点、状态定义和条件路由应保持边界清晰。
- 工作流只依赖统一 `LLMService`；模型选择、服务实例创建和厂商 API 调用分别由 Model Router、LLMServiceFactory 和厂商 service 承担。
- 模型调用、Token 计量、向量存储、文档解析和工作流编排应避免紧密绑定到单一业务节点。
- 非敏感模型配置应外置到版本化配置文件，密钥通过 `.env` 注入，便于本地开发和 Docker 部署分别配置。

## 12. 验收标准

| 编号 | 验收条件 |
| --- | --- |
| AC-01 | 输入主题、页数、受众和风格后，系统能够生成可检查的结构化需求。 |
| AC-02 | 系统生成包含章节、子主题和页面分配的大纲，分配页数总和等于目标页数。 |
| AC-03 | 上传支持格式的参考文件后，系统显示解析状态，并能在生成流程中检索该任务的资料片段。 |
| AC-04 | 系统输出的页面数量与目标页数一致，页码连续，每页至少有标题和核心要点。 |
| AC-05 | 后台 Agent 评估结果包含总分、通过状态、问题列表和修改建议，并可驱动自动修订；正常用户流程不要求打开评估页面。 |
| AC-06 | 评估未通过时系统按配置在后台进入修订和重评；到达上限后停止自动循环，并在内容工作台提供继续编辑、聊天修改、局部重生成或确认当前内容的操作。 |
| AC-07 | 用户可在内容工作台确认正文、提交反馈或指定重生成范围；系统在恢复流程时使用该反馈，确认正文后进入最终结果页。 |
| AC-08 | 用户可以预览、复制或下载最终 Markdown，文件结构清晰且内容与页面结果一致。 |
| AC-09 | 文件解析、检索、模型调用或生成失败时，系统展示失败环节和可理解的错误提示，不将失败结果标为成功。 |
| AC-10 | 当前任务的资料和状态不会被其他任务错误引用；敏感模型配置不会暴露给前端。 |
| AC-11 | 用户在大纲页面通过聊天说“把第四点改成具体项目分析”时，系统能修改对应大纲条目并展示更新结果；目标不明确时会先追问。 |
| AC-12 | 若大纲条目对应页面已经生成，系统会指出受影响的页面并询问是否重新生成；用户选择后只处理相关页面。 |
| AC-13 | 用户在内容页面通过聊天提出章节级修改后，系统会更新指定范围、保留无关页面，并对变更内容重新评估。 |
| AC-14 | 对话记录和修改结果与当前任务关联；刷新或恢复任务后，用户仍能查看此前对话及已应用的修改。 |
| AC-15 | 自动模式能按配置的复杂度规则为简单、普通和复杂任务选择相应模型档位，并保存选择依据。 |
| AC-16 | 用户生成前手动指定模型时，该模型作为首选模型生效，并在生成页面显示。 |
| AC-17 | 首选 GLM 遇到可恢复服务故障并达到重试上限后，系统按配置切换到 DeepSeek Pro 等备用模型，并向用户展示实际模型和切换原因。 |
| AC-18 | 每次 Agent 模型调用均可追溯首选模型、实际模型、所属节点、重试和降级情况。 |
| AC-19 | 备用模型调用成功后，工作流从失败节点继续，保留已完成结果；生成内容仍进入质量评估。 |
| AC-20 | 首选和备用模型均失败时，任务停留在可恢复状态，显示失败节点和错误类型，并允许用户调整模型后继续。 |
| AC-21 | `GET /tasks/{taskId}/token-usage` 返回该任务的输入、输出和总 Token 汇总，并能按模型、节点查看用量及逐次调用明细。 |
| AC-22 | 同一请求发生两次重试并随后降级成功时，四次实际尝试分别记录并计入任务汇总；重复处理同一调用记录不会重复累计。 |
| AC-23 | 供应商未返回 usage 的失败调用显示 `usage_status=unavailable`，任务汇总标记为不完整，而不是将该次用量记为 0。 |
| AC-24 | Model Router 选择任一首期模型后，LLMServiceFactory 能按 provider 返回 DeepSeekService 或 GLMService；工作流节点无需知道厂商 SDK。 |
| AC-25 | 模型目录同时包含 DeepSeek Flash、DeepSeek Pro、GLM-4.7-Flash 和 GLM-5.3-Flash；修改模型 ID、服务地址或备用链只需调整非敏感配置，不需修改工作流代码。 |
| AC-26 | `.env` 和部署环境只承载 API Key 等敏感值，仓库中的 `.env.example` 不含真实密钥，模型 ID、base URL、超时和路由规则不写入 `.env`。 |
| AC-27 | 端到端用户路径为“需求与文件 → 可编辑/可聊天的大纲 → 含资料检索且可编辑/可聊天的内容工作台 → 最终结果与 Markdown 下载”；质量评估只在后台 Agent 闭环中出现。 |
| AC-28 | 用户上传的同一任务资料既能为大纲生成提供检索上下文，也能在内容生成时按章节/页面重新检索，且不会引用其他任务文件。 |

## 14. 建议实施阶段

阶段顺序沿用项目说明中的规划，并将每阶段的可交付结果具体化：

1. **LLM 基础**：完成统一 LLMService、DeepSeekService、GLMService、LLMServiceFactory、四模型目录、路由配置、提示词调用和调用级 Token usage 记录。
2. **RAG 模块**：完成文件上传、解析、切分、向量索引和检索，并能查看来源信息。
3. **LangGraph 工作流**：完成 SlideState、Requirement、Planner、Research、Writer 节点、按复杂度选模及条件路由。
4. **质量闭环**：完成 Evaluator、Refiner、修订计数和有限后台循环，不增加用户流程页面。
5. **Human-in-the-loop**：完成反馈提交、流程暂停、状态持久化和恢复。
6. **系统工程化**：完成 Vue 3 界面、FastAPI 接口、任务 Token 汇总接口、Markdown 导出、上下文聊天助手、模型选择与降级状态展示、错误处理和 Docker 部署。

建议先以一条端到端场景验收首期：用户输入需求并上传一份行业报告，系统利用资料生成可编辑大纲；用户通过直接编辑和聊天确认大纲后，系统检索资料并生成可编辑正文；后台自主评估及有限修订；用户确认正文后查看并下载 Markdown，同时能查询该任务完整的 Token 消耗。

## 15. 需求基线摘要

SlideAI 首期的核心价值是让用户沿着“需求与文件 → 可编辑/可聊天的大纲 → 含资料检索且可编辑/可聊天的内容工作台 → 最终结果与 Markdown 下载”得到逐页演示文稿文案。系统通过 LangGraph 管理需求解析、规划、检索、写作、后台评估和修订状态；模型路由器、模型服务工厂与 DeepSeek/GLM service 协作调用四款模型，在服务故障时受控降级，并按调用及任务记录 Token 消耗。

首期验收应优先保证端到端用户链路、页数和结构约束、上传资料同时服务大纲和内容生成、四款模型可通过 Factory 和厂商 service 调用、模型能够自动分层选择且允许用户手动指定首选、模型故障可以按配置降级、每个任务 Token 可完整追溯、后台评估返工有上限、用户可在大纲及内容工作台直接或通过聊天修改，以及 Markdown 可用。PPTX 排版、多用户协作和互联网搜索等扩展能力应在核心链路完成后另行确定。
