# SlideAI 需求分析

> 文档版本：1.0  
> 编写日期：2026-09-28  
> 依据文档：项目说明.md  
> 文档用途：作为 SlideAI 首期产品实现、范围管理和验收的需求基线。

## 1. 项目概述

### 1.1 项目定位

SlideAI 是面向技术汇报、行业分析和企业方案等场景的演示文稿内容生成与优化系统。用户提交主题、受众、页数、风格等要求，可附上参考资料。系统通过需求解析、结构规划、知识检索、逐页写作、质量评估和定向修订，生成结构化 Markdown 演示文稿内容。

系统重点解决长内容生成中的规划、资料利用、质量检查和反复修改问题。系统生成的是可继续编辑的演示文稿文案，不负责首期的视觉排版或 PPTX 文件制作。

### 1.2 目标用户

| 用户 | 主要目标 | 典型操作 |
| --- | --- | --- |
| 内容创作者 | 更快完成有结构、有资料依据的演示文稿内容 | 填写要求、上传材料、检查大纲、修改结果、导出 Markdown |
| 系统维护者 | 配置和维护模型及运行环境 | 配置模型服务、查看运行日志、维护部署环境 |

首期重点服务内容创作者。系统维护者的高级运营、组织管理和权限管理能力不属于首期核心范围。

### 1.3 用户问题

当前演示文稿内容通常需要人工完成资料搜集、结构设计、逐页写作和多轮检查。直接让大语言模型一次性生成，容易出现结构松散、内容重复、资料利用不足和质量难以判断等问题。SlideAI 通过有状态的工作流和评测返工机制，将这些步骤组织成可检查、可修改的过程。

## 2. 需求来源与约定

### 2.1 标记说明

- **明确要求**：项目说明.md 已直接提出的能力或边界。
- **落地建议**：为使需求可实现、可操作、可验收而补充的建议；需在正式实现前确认具体取值。
- **待确认**：项目说明尚未定义，本文先记录为决策项，不假定为已确定事实。

### 2.2 优先级说明

- **P0**：首期可用版本必须具备。
- **P1**：完善首期体验或可靠性的重要能力，可在核心链路之后实现。
- **P2**：后续增强能力，当前不作为首期验收阻塞项。

## 3. 产品目标与成功标准

### 3.1 产品目标

1. 用户能够通过 Web 界面提交演示文稿需求。
2. 系统能够解析需求并规划章节、子主题和页数分配。
3. 系统能够使用用户上传的资料为内容生成提供检索依据。
4. 系统能够按指定页数生成逐页内容，并以 Markdown 形式交付。
5. 系统能够评估内容质量；评估不通过时自动修订并重新评估。
6. 用户能够补充修改意见、审核结果，并在自动优化达到上限时继续控制生成过程。
7. 系统能够根据任务复杂度和用户选择，为各 Agent 调用合适的模型，并在首选模型发生可恢复故障时使用配置的备用模型。

### 3.2 首期成功标准

以下是建议的首期验收结果：

- 从填写需求到得到 Markdown 的主要路径能够完整运行。
- 生成结果页数符合用户要求，每页具有标题和核心内容。
- 用户上传的支持格式文件能够进入解析和检索流程；解析失败时能看到具体文件及原因。
- 评估结果能够说明评分、问题和修改建议。
- 未通过的结果能够进入有限次数的自动修订；达到上限后能够交由用户处理。
- 系统能根据任务复杂度自动选择模型，允许用户在生成前指定首选模型，并在可恢复故障时按配置降级。
- 用户可以将结果复制或下载为 Markdown 文件。

本项目说明未给出响应时间、准确率或通过分数等定量指标。相关指标在第 13 节列为待确认项。

## 4. 范围定义

### 4.1 首期范围

首期包含：

- 演示文稿需求录入和结构化解析；
- 按任务难度自动选择模型、生成前手动选择首选模型，以及模型请求失败后的自动降级；
- 在大纲和最终内容页面提供上下文聊天助手，支持用户以自然语言讨论并修改内容；
- 大纲规划及页面分配；
- PDF、Markdown、TXT、Word 资料上传和解析；
- 基于上传资料的向量检索增强生成；
- 逐页内容生成；
- 内容质量评估；
- 自动修订和重新评估；
- 用户反馈、审核和局部重生成；
- Markdown 结果预览、复制或下载；
- FastAPI 服务、Vue 3 前端及 Docker 部署基础。

### 4.2 首期不包含

以下能力未在项目说明中列为首期目标，暂不纳入首期验收：

- 直接生成或编辑 PPTX 文件；
- 幻灯片视觉设计、模板套用和图表排版；
- 未经用户提供资料的互联网实时搜索；
- 多人实时协作、组织空间、计费或复杂权限管理；
- 对生成内容事实正确性作绝对保证；
- 用户自建、管理多个长期共享知识库。

后续如需加入，应另行定义范围及验收标准。

## 5. 典型用户场景

### 5.1 根据参考资料生成演示文稿

1. 用户输入主题、页数、使用场景、目标受众、风格和特殊限制。
2. 用户上传参考行业报告。
3. 系统解析需求和文件，反馈无法识别或无法解析的输入。
4. Requirement Agent 形成结构化需求；Planner Agent 生成大纲和页数分配。
5. Research Agent 从上传资料中检索相关内容。
6. Writer Agent 生成逐页文案。
7. Evaluator Agent 检查页数、覆盖度、逻辑、内容质量和需求符合度。
8. 未通过时，Refiner Agent 按评估意见修订，再次评估。
9. 用户查看结果、提交修改意见或接受结果。
10. 系统输出可复制或下载的 Markdown 文档。

### 5.2 在最终内容阶段通过聊天助手修改正文

用户在最终内容页面通过聊天助手提出“第三章减少技术细节，增加商业应用案例”等要求。系统以当前演示文稿及目标章节、页面为上下文，定向修订正文，展示修改结果并重新评估；未涉及的页面应保持不变。

### 5.3 自动修订达到上限

系统达到配置的最大自动修订次数仍未通过评估时，应停止自动循环，向用户展示当前内容、评估结果和修改建议，并允许用户接受、补充意见或指定重生成范围。

### 5.4 在大纲阶段通过聊天助手调整结构

用户在大纲页面对助手说“把第四点改成具体项目分析”。助手结合当前大纲确定目标条目，更新其标题或内容并展示修改结果。如果该条目已经对应生成页面，系统应列出受影响页面并询问用户是否重新生成，避免大纲与现有正文不一致。

### 5.5 根据任务难度选择模型并在故障时降级

用户可以在生成前选择自动模式或指定首选模型。自动模式根据任务页数、专业程度、资料规模和限制复杂度分配模型；例如，高复杂度任务优先使用 GLM，普通任务使用 DeepSeek Pro，简单任务使用 DeepSeek Flash。若 GLM 请求超时或服务暂不可用，系统按备用顺序切换到 DeepSeek Pro，并告知用户本次实际使用的模型。示例名称和映射可由部署配置调整。

## 6. 功能需求

### 6.1 需求录入与解析

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-REQ-01 | P0 | 用户可以填写主题、目标页数、使用场景、目标受众、内容风格和特殊限制。主题为必填项；其余字段按产品配置为必填或选填。 |
| FR-REQ-02 | P0 | 系统应将原始输入解析为结构化需求，至少包含主题、页数、受众和风格，并保留场景、限制及用户原文。 |
| FR-REQ-03 | P1 | 对缺失、冲突或无法理解的关键条件，系统应标明问题并允许用户补充或修正，不应悄悄将推测值当作用户要求。 |
| FR-REQ-04 | P1 | 用户可以在正式生成前查看并修改结构化需求。 |

结构化需求建议至少包含：主题、目标页数、场景、受众、风格、特殊限制、语言、资料使用偏好和原始描述。语言、资料使用偏好属于落地建议。

### 6.2 大纲规划

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-OUT-01 | P0 | Planner Agent 根据结构化需求生成包含章节、子主题和页面分配的大纲。 |
| FR-OUT-02 | P0 | 页面分配之和必须与用户要求页数一致；若无法合理分配，系统应调整大纲或提示用户，而非静默改变页数。 |
| FR-OUT-03 | P1 | 用户可以查看并编辑大纲，确认后再生成全部页面内容。 |
| FR-OUT-04 | P1 | 大纲应体现目标受众、使用场景、风格和特殊限制。 |
| FR-OUT-05 | P0 | 用户可以在大纲页面通过聊天助手提出修改要求；助手应把清晰、指向明确的要求应用到对应大纲条目，并展示更新后的大纲。 |

### 6.3 资料上传、解析与检索

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-RAG-01 | P0 | 用户可以上传 PDF、Markdown、TXT 和 Word 文档作为本次生成的参考资料。 |
| FR-RAG-02 | P0 | 系统应校验文件格式，并对文件进行文本解析、切分、向量化和索引。 |
| FR-RAG-03 | P0 | Research Agent 应根据主题、大纲和页面内容需要，从已上传资料中检索相关文本，并将检索结果提供给 Writer Agent。 |
| FR-RAG-04 | P0 | 系统应显示各文件的处理状态；文件解析失败时应显示可理解的错误原因，并允许用户移除文件或重新上传。 |
| FR-RAG-05 | P1 | 检索片段应保留来源文件信息；在解析能力允许时保留页码或章节信息。 |
| FR-RAG-06 | P1 | 生成内容应能标示引用或资料依据，使用户可以识别内容与来源资料的关系。 |

PDF 页码、Word 段落或标题等定位方式可能因解析库而异，应在实现方案中明确。引用展示格式属于待确认项。

### 6.4 页面内容生成

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-WR-01 | P0 | Writer Agent 应依据需求、大纲和检索结果生成每页内容。 |
| FR-WR-02 | P0 | 每页至少包含页码、标题和核心要点；可以包含讲解说明或演讲备注。 |
| FR-WR-03 | P0 | 生成页数应与目标页数一致，页码连续，不应出现空白页或重复页面。 |
| FR-WR-04 | P0 | 内容应遵守目标受众、风格及用户提出的限制。 |
| FR-WR-05 | P1 | 对缺少资料支撑的判断或事实，系统应避免伪造来源；可将不确定内容标记为待核实。 |
| FR-WR-06 | P1 | 用户可以指定页面或章节进行重生成，并尽可能保留未指定部分。 |

### 6.5 质量评估

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-EVA-01 | P0 | Evaluator Agent 应检查完整性、逻辑性、内容质量和用户需求符合度。 |
| FR-EVA-02 | P0 | 评估结果应包含总分、是否通过、问题列表和修改建议。 |
| FR-EVA-03 | P1 | 系统应检查明确的硬性条件，包括页数、必需章节或主题覆盖要求。 |
| FR-EVA-04 | P1 | 用户应能够查看评估结果，并了解哪些问题触发了修订。 |

通过分数、分项权重和硬性条件的规则尚未在项目说明中定义，应采用可配置规则，并在开发前确定首期默认值。

### 6.6 自动优化与流程控制

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-LOOP-01 | P0 | 评估通过时，工作流进入结果输出阶段。 |
| FR-LOOP-02 | P0 | 评估未通过时，Refiner Agent 应根据当前内容、问题和建议生成修订版本。 |
| FR-LOOP-03 | P0 | 修订后应重新评估；工作流应避免无限循环，并记录修订次数。 |
| FR-LOOP-04 | P0 | 达到最大修订次数仍未通过时，工作流应暂停并请求用户处理。 |
| FR-LOOP-05 | P1 | Supervisor 应根据当前状态选择下一节点，并记录节点结果、评估结果和修订历史。 |

### 6.7 人工反馈与审核

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-HITL-01 | P0 | 用户可以接受当前结果、提交修改建议或指定重新生成范围。 |
| FR-HITL-02 | P0 | 用户反馈应被写入工作流状态，并在恢复执行时提供给相关 Agent。 |
| FR-HITL-03 | P1 | 工作流暂停后应能够基于保存的状态恢复，避免从头重复解析和生成。 |
| FR-HITL-04 | P1 | 用户提交的反馈应作用于指定章节或页面；未指定范围时系统应先说明理解的修改范围。 |

### 6.8 聊天助手交互

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-CHAT-01 | P0 | 大纲页面和最终内容页面均应提供聊天助手入口，助手应读取当前任务及当前展示的大纲、页面内容和评估结果作为对话上下文。 |
| FR-CHAT-02 | P0 | 用户可以用自然语言修改大纲或内容，例如“把大纲第四点改成具体项目分析”或“第三章减少技术细节，增加商业案例”。 |
| FR-CHAT-03 | P0 | 助手应识别用户指向的章节、条目或页面；指向不明确或要求存在冲突时，应先追问，不得静默修改错误范围。 |
| FR-CHAT-04 | P0 | 修改请求必须落实到结构化大纲或页面内容及工作流状态中；助手应展示修改后的结果，而不能只返回文字建议。 |
| FR-CHAT-05 | P0 | 大纲修改影响已生成页面时，助手应列出受影响范围，并让用户选择是否重新生成相关页面；不得未经提示就重生成整份文稿。 |
| FR-CHAT-06 | P0 | 内容修改应按识别出的页面或章节定向执行，并对修改后的内容重新评估。 |
| FR-CHAT-07 | P1 | 用户选中某个大纲条目或页面后，可以将其作为明确的对话对象；助手也应能处理用户在消息中直接说明的目标范围。 |
| FR-CHAT-08 | P1 | 对话历史、目标对象、修改请求及执行结果应关联到生成任务，并在任务恢复后可查看。 |
| FR-CHAT-09 | P1 | 单一且明确的局部修改完成后，助手应展示修改摘要和结果并提供撤销或再次修改入口；影响大范围内容或改变页数等关键约束时，应先展示方案并征求用户确认。 |

推荐交互流程：用户在大纲或内容页面打开侧边聊天面板并描述修改；助手结合当前页面上下文解析目标；不明确时追问；明确后应用定向修改并显示结果。若大纲修改会影响已生成页面，先展示影响页面和重新生成选项。具体页面布局由 UI 设计阶段确定。

### 6.9 Markdown 输出与前端交互

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-UI-01 | P0 | Vue 3 前端应提供需求录入、文件上传、生成状态和结果查看的基本页面。 |
| FR-UI-02 | P0 | 用户应能查看大纲、逐页内容和最终评估结果。 |
| FR-UI-03 | P0 | 系统应生成结构清晰、页码明确的 Markdown 文档。 |
| FR-UI-04 | P0 | 用户应能复制 Markdown 内容或下载 Markdown 文件。 |
| FR-UI-05 | P1 | 长时间生成过程中，前端应展示当前阶段和可理解的状态信息。 |
| FR-UI-06 | P1 | 发生模型、检索、文件解析或服务错误时，前端应显示失败环节和可执行的后续操作。 |
| FR-UI-07 | P0 | 大纲和最终内容页面应展示与当前任务关联的聊天助手面板；用户可以边查看内容边对话，修改结果应同步反映在当前页面。 |
| FR-UI-08 | P0 | 用户开始生成前应能选择自动选模或指定可用的首选模型；生成过程中及结果页应显示当前选择、实际调用模型和是否发生降级。 |

建议的 Markdown 结构为：文档标题、需求摘要、大纲、逐页标题与要点、说明或备注、资料引用（如启用）。具体模板待确认。

### 6.10 模型分层、自动选择与故障降级

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-MODEL-01 | P0 | 系统应提供可配置的模型目录，将可用模型映射为快速/经济、均衡和高级等能力档位；模型提供商、实际模型 ID 和显示名称不得硬编码在工作流逻辑中。 |
| FR-MODEL-02 | P0 | 自动模式应根据任务页数、领域专业程度、参考资料规模、约束数量及分析深度等因素评估任务复杂度，并选择适当档位。首次路由可使用已填写需求和文件元数据进行初步估计；需求解析后应更新复杂度，再为后续节点选模。 |
| FR-MODEL-03 | P0 | 模型路由应按任务复杂度及调用节点，为需求解析、大纲规划、页面写作、评估和返工等模型调用选择模型。具体节点映射应可配置。 |
| FR-MODEL-04 | P0 | 用户可以在生成前选择自动选模，或指定一个首选模型；手动选择时优先采用该模型，不再按自动复杂度替换首选模型。 |
| FR-MODEL-05 | P0 | 每个首选模型应支持配置备用模型及顺序。首选模型遇到超时、网络故障、限流或服务端错误等可恢复故障时，系统在有限重试后应切换到能力兼容的备用模型。示例备用链为 GLM → DeepSeek Pro → DeepSeek Flash。 |
| FR-MODEL-06 | P0 | 用户手动选择的模型仍可按已配置策略自动降级；降级后系统应明确告知用户实际使用的模型及降级原因。 |
| FR-MODEL-07 | P0 | 系统应按每次模型调用记录所选档位、首选模型、实际模型、调用节点、重试/降级情况和结果状态。 |
| FR-MODEL-08 | P0 | 所有备用模型均不可用时，系统应保留任务现场，指出失败节点和错误类型，并允许重试或调整模型后继续。 |
| FR-MODEL-09 | P1 | 自动选模应能说明档位选择的主要依据；任务运行中不得丢失此前已完成的节点结果。 |
| FR-MODEL-10 | P1 | 对认证、参数或输出格式等非服务暂时故障，系统应区分错误类型并给出处理提示，避免无意义地重复调用同一备用链。 |

建议的示例映射如下。DeepSeek Flash、DeepSeek Pro 和 GLM 是当前需求中采用的模型档位示例；正式模型名称及供应商 API 模型 ID 通过配置确定。

| 能力档位 | 示例模型 | 适用任务 | 示例备用 |
| --- | --- | --- | --- |
| 快速/经济 | DeepSeek Flash | 简单主题、短文稿、需求提取和轻量总结 | 按可用模型目录配置 |
| 均衡 | DeepSeek Pro | 常规大纲、逐页写作和内容评估 | DeepSeek Flash |
| 高级 | GLM | 高页数、复杂约束、专业分析或需要多步推理的任务 | DeepSeek Pro，其次 DeepSeek Flash |

用户选择的首选模型应作为整个任务的默认偏好；节点能力映射和故障降级仍可使用配置策略。自动模式可以按节点选择不同档位。模型路由器应优先使用规则化特征和结构化复杂度结果，记录选择依据并提供稳定、可复现的路由行为。


## 7. Agent 职责与边界

| Agent / 组件 | 职责 | 主要输入 | 主要输出 |
| --- | --- | --- | --- |
| Supervisor | 编排工作流、维护状态、处理条件路由 | 当前 SlideState | 下一节点、流程状态 |
| Model Router（模型路由器） | 根据任务复杂度、用户首选和节点策略选择模型；处理受控重试和备用模型切换 | 任务状态、节点类型、用户模型偏好、模型目录 | 实际模型、路由原因、重试或降级记录 |
| Requirement Agent | 提取和规范用户需求 | 用户原始输入 | 结构化需求 |
| Planner Agent | 规划章节、子主题及页数分配 | 结构化需求 | 大纲 |
| Research Agent | 检索资料并整理依据 | 需求、大纲、资料索引 | 检索片段及来源信息 |
| Writer Agent | 生成或按反馈修订页面内容 | 需求、大纲、资料、反馈 | 逐页内容 |
| Evaluator Agent | 按质量维度评估内容 | 需求、大纲、逐页内容 | 分数、通过状态、问题和建议 |
| Refiner Agent | 根据评估意见优化内容 | 当前内容、评估结果 | 修订后的内容 |
| Markdown Generator | 将结构化结果组织为 Markdown | 需求、大纲、页面、评估和来源 | 最终 Markdown |
| 对话助手（交互层） | 结合页面上下文理解修改意图、追问歧义并将明确请求路由到相应工作流节点 | 当前任务、对话消息、选中条目或页面 | 结构化修改请求、澄清问题、执行结果 |

对话助手负责把自然语言转换为有目标范围的工作流操作；具体修改仍由大纲或内容节点执行，并进入相应评估流程。是否将其实现为独立 Agent 属于技术设计选择。

各 Agent 应通过明确的状态字段交换结果，避免依赖不可追踪的隐式对话上下文。

## 8. 业务规则与工作流状态

### 8.1 主工作流

需求提交及模型偏好设置 → 初步复杂度估计 → Requirement Agent 解析需求 → 更新复杂度并选择后续模型 → 大纲规划 → 资料检索 → 页面生成 → 质量评估 → 条件路由 → Markdown 输出或修订循环 → 用户审核/反馈 → 完成。

首次需求解析使用用户指定的首选模型；自动模式依据已填写字段和上传文件元数据进行初步选模。解析出完整需求后，系统更新复杂度，并为后续模型调用重新路由。Model Router 在每个模型调用前结合当前复杂度、任务级手动首选和节点策略选出实际模型。模型调用发生可恢复故障时，按有限重试和备用链执行；调用恢复后工作流从失败节点继续，不重复已完成节点。

在大纲确认和最终内容查看阶段，用户也可以通过聊天助手提交修改。助手将请求路由到大纲修改或页面修订流程；修改完成后更新当前内容，必要时重新评估。

- 评估通过：生成最终 Markdown，流程完成。
- 评估未通过且仍可修订：进入 Refiner，再次生成或修订并评估。
- 评估未通过且已达修订上限：进入等待用户反馈状态。
- 用户提出修改：保存反馈后恢复相关节点。
- 用户接受结果：将任务标记为完成。

### 8.2 状态字段

项目说明提出的核心 SlideState 字段为：

- user_requirement：结构化用户需求；
- outline：演示文稿大纲；
- retrieved_documents：检索到的资料片段；
- slides_content：逐页内容；
- evaluation_result：评估结果；
- revision_count：修订次数；
- human_feedback：人工反馈；
- conversation_history：聊天消息、当前对话目标及助手执行结果；
- pending_change：等待用户确认或补充信息的修改请求；
- model_preference：用户选择的自动模式或首选模型；
- task_complexity：自动模式得出的复杂度及判断依据；
- model_call_history：各节点的所选模型、实际模型、重试和降级记录；
- final_markdown：最终 Markdown。

落地建议补充任务标识、当前节点、任务状态、文件处理状态、错误信息、修订历史和时间信息，以支持前端展示、故障恢复和审计。

### 8.3 状态建议

任务状态建议至少包含：待处理、处理中、等待用户反馈、已完成、失败、已取消。实际状态名可以按实现统一，但前后端含义必须一致。

## 10. 外部接口与工具需求

### 10.1 后端接口职责

后端通过 FastAPI 提供前端所需能力，至少覆盖：

- 创建生成任务并提交需求；
- 获取可选模型及能力档位，并在任务创建时提交自动模式或首选模型；
- 查看任务各节点实际调用的模型及降级状态；
- 在任务上下文中发送聊天消息、获取澄清问题或修改结果；
- 上传、查看和移除任务资料；
- 查看任务状态、当前阶段和错误信息；
- 查看或修改大纲；
- 提交用户反馈、审核结论或局部重生成请求；
- 获取、预览和下载最终 Markdown。

具体 HTTP 路径、请求字段、流式状态推送方式和鉴权策略属于技术设计阶段内容。

### 10.2 Agent 工具

- Knowledge Search：在当前任务的知识索引中检索相关内容。
- Document Analyzer：解析用户上传的资料。
- Content Evaluation：执行可复用的内容检查。
- Markdown Generator：把结构化结果转换为最终文档。

Agent 对工具调用失败应能识别并将错误反馈到工作流状态，不能将工具错误伪装成成功结果。

## 11. 非功能需求

以下指标中，项目说明未明确量化值的部分均为落地建议，需结合部署环境确认。

### 11.1 易用性

- 表单字段应有清晰说明和输入校验。
- 页面应区分生成阶段、等待用户处理和最终结果。
- 评估意见应能直接帮助用户决定如何修改。

### 11.2 可靠性

- 工作流应记录修订次数并设置最大值。
- 节点失败时应保留足以定位问题的任务状态。
- 模型调用应区分可恢复服务故障和配置/输入错误；可恢复故障按有限重试和备用链处理。
- 模型切换后应从失败节点恢复，保留已完成结果，避免用户重复提交整个任务。
- 对可重试的模型或检索错误，应允许用户重试或恢复任务。
- 长任务应支持状态查询；若要求用户中断后继续，需实现持久化检查点。

### 11.3 安全与隐私

- 上传文件类型和大小应由服务端校验，不能只依赖浏览器校验。
- 文件内容不得被解释为系统指令；资料只作为检索上下文使用。
- 模型密钥等敏感配置应放在服务端配置中，不应返回前端或写入普通日志。
- 任务资料和生成内容不应在不同用户或任务间意外混用。
- 文件大小限制、保留期限、传输和存储保护要求需在部署前明确。

### 11.4 性能

- 文件解析、向量化和生成可能耗时较长，应采用可查询状态的任务流程。
- 首期应避免同步请求因长时间生成而超时。
- 单文件大小、单任务文件数、最大页数和并发任务量待根据运行环境确定。

### 11.5 可维护性

- Agent 节点、状态定义和条件路由应保持边界清晰。
- 模型调用、向量存储、文档解析和工作流编排应避免紧密绑定到单一业务节点。
- 关键配置应外置，便于本地开发和 Docker 部署分别配置。

| AC-18 | 每次 Agent 模型调用均可追溯首选模型、实际模型、所属节点、重试和降级情况。 |

| AC-20 | 首选和备用模型均失败时，任务停留在可恢复状态，显示失败节点和错误类型，并允许用户调整模型后继续。 |

## 14. 建议实施阶段

阶段顺序沿用项目说明中的规划，并将每阶段的可交付结果具体化：

1. **LLM 基础**：完成模型提供商配置、模型目录和能力档位、提示词调用及单次页面内容生成。
2. **RAG 模块**：完成文件上传、解析、切分、向量索引和检索，并能查看来源信息。
3. **LangGraph 工作流**：完成 SlideState、Requirement、Planner、Research、Writer 节点、按复杂度选模及条件路由。
4. **质量闭环**：完成 Evaluator、Refiner、修订计数和有限循环。
5. **Human-in-the-loop**：完成反馈提交、流程暂停、状态持久化和恢复。
6. **系统工程化**：完成 Vue 3 界面、FastAPI 接口、Markdown 导出、上下文聊天助手、模型选择与降级状态展示、错误处理和 Docker 部署。

建议先以一条端到端场景验收首期：用户上传一份行业报告，要求生成指定页数的专业汇报，系统能够检索资料、生成逐页内容、评估、必要时修订并导出 Markdown。

## 15. 需求基线摘要

SlideAI 首期的核心价值是让用户得到一份经过结构规划、参考资料增强和质量检查的逐页演示文稿文案。系统通过 LangGraph 管理需求解析、规划、检索、写作、评估、修订和人工反馈状态；模型路由器按复杂度、用户首选和节点策略调度模型，并在服务故障时受控降级；前端负责提交需求、上传资料、选择模型、查看过程与结果；最终以 Markdown 交付。

首期验收应优先保证端到端链路、页数和结构约束、上传资料可检索、模型能够自动分层选择且允许用户手动指定首选、模型故障可以按配置降级、评估返工有上限、人工反馈可生效、用户可在大纲及内容页面通过聊天助手直接修改当前任务，以及 Markdown 可用。PPTX 排版、多用户协作和互联网搜索等扩展能力应在核心链路完成后另行确定。
