# SlideAI
## 基于 LangGraph 的智能演示文稿内容生成与优化系统

---

# 1. 项目概述

## 1.1 项目名称

SlideAI

英文名称：

Agent-powered Presentation Content Generation and Optimization System


---

## 1.2 项目简介

SlideAI 是一个基于大语言模型（LLM）和多智能体协作（Multi-Agent）的智能演示文稿内容生成系统。

系统面向技术汇报、行业分析、企业方案等内容创作场景，通过多个智能体协同完成：

- 用户需求理解；
- 演示文稿结构规划；
- 知识检索增强；
- 页面内容生成；
- 内容质量评测；
- 自动优化返工；
- 多模型路由与故障降级；
- 任务级 Token 消耗统计；

最终输出结构化 Markdown 文档。


区别于传统 LLM 单轮生成方式，SlideAI 引入：

- LangGraph 工作流编排；
- Agent 间任务协作；
- Evaluation-Reflection 优化机制；
- Human-in-the-loop 人机协同机制；

实现一个具有规划、执行、评估、修正能力的智能内容生成 Agent 系统。

# 2. 项目背景

## 2.1 问题背景

传统演示文稿制作流程：
```
确定主题

↓

人工收集资料

↓

设计结构

↓

编写内容

↓

人工检查修改
```
存在：

- 制作周期长；
- 信息整理成本高；
- 内容质量依赖个人经验；
- 修改优化过程重复；

等问题。


---

## 2.2 LLM应用局限

直接使用大语言模型生成 PPT 内容：
```
用户输入需求

↓

LLM

↓

输出内容
```
存在：

- 缺少整体规划；
- 长文本任务容易失控；
- 内容质量无法保证；
- 缺少自动优化机制。


因此，需要引入 Agent 架构，使模型能够：
```
规划任务

↓

调用工具

↓

生成内容

↓

评价结果

↓

自主优化
```

# 3. 项目目标


## 3.1 核心目标

实现一个智能演示文稿内容生成 Agent。

用户输入：
```
主题：
人工智能发展趋势

要求：
生成15页技术汇报

目标：
企业技术人员

风格：
专业简洁
```
用户与系统协同完成：
```
用户输入需求 + 上传文件

↓

系统生成大纲（使用上传资料）

↓

用户直接编辑或通过聊天修改大纲

↓

资料检索 + 页面内容生成

↓

用户直接编辑或通过聊天修改内容

↓

后台 Agent 自主质量评测与有限优化

↓

最终结果展示 + Markdown 下载
```

质量评测和自动优化是 Agent 的内部闭环，不是用户流程中的独立页面或确认步骤。用户需要操作的主线固定为：需求与文件、大纲编辑与对话、内容编辑与对话、最终结果与 Markdown 下载。

# 4. 核心功能设计


# 4.1 用户需求解析


用户输入：

- 主题
- 页数
- 使用场景
- 目标对象
- 风格要求
- 特殊限制


Requirement Agent 输出结构化信息：

```json
{
 "topic":"人工智能发展趋势",
 "page_num":15,
 "audience":"技术人员",
 "style":"专业"
}
```

------

# 4.2 演示文稿大纲规划

Planner Agent 根据需求生成：

- 一级章节；
- 二级内容；
- 页面分配。

Planner Agent 还应使用本任务已上传并完成解析的资料，通过主题级和结构级检索获取大纲依据。用户可以在大纲页面直接增删、改名、排序和调整页数，也可以通过聊天助手用自然语言修改大纲；确认大纲后才进入内容生成。

示例：

```
第一章 人工智能发展背景

1.1 AI发展历程

1.2 当前技术趋势


第二章 大语言模型

2.1 Transformer架构

2.2 大模型应用


第三章 未来趋势
```

------

# 4.3 RAG知识增强

支持用户上传：

- PDF
- Markdown
- TXT
- Word

建立知识库：

```
文档

↓

解析

↓

文本切分

↓

Embedding

↓

向量数据库

↓

Retriever

↓

相关知识
```

生成大纲和内容时：

Research Agent 使用同一任务的资料索引自动检索相关内容：大纲阶段按主题和结构目标检索，内容阶段按章节及页面目标重新检索。任何检索都必须限定当前任务，不得跨任务引用资料。

------

# 4.4 页面内容生成

Writer Agent 根据：

- 大纲
- 检索资料
- 用户需求

生成：

每页内容。

格式：

```
第1页

标题：
人工智能发展历程


核心内容：

- 1956年人工智能概念提出
- 深度学习推动AI发展
- 大模型开启新阶段


说明：

介绍AI技术演进过程
```

内容生成完成后进入内容工作台。用户可以直接编辑标题、要点和备注，也可以通过聊天助手定向修改章节或页面；未指定范围的内容必须保持不变。用户确认当前正文后，系统才生成并展示最终 Markdown。

------

# 4.5 内容质量评测

引入：

Evaluator Agent

负责对生成内容进行自动评价。

本节由 Agent 在后台自主执行。评测结果供 Supervisor 和 Refiner 决定是否自动修订，也可以作为诊断信息保存，但不构成用户必须经过的流程阶段、独立页面或确认表单。

评价维度：

## 完整性

检查：

- 是否覆盖主题；
- 是否满足页数；
- 是否缺少关键章节。

------

## 逻辑性

检查：

- 内容组织是否合理；
- 页面之间是否存在跳跃。

------

## 内容质量

检查：

- 信息密度；
- 是否空泛；
- 是否存在重复。

------

## 用户需求符合度

检查：

- 是否符合目标用户；
- 是否符合指定风格。

------

Evaluator 输出：

```
{
 "score":85,

 "pass":true,

 "issues":[
 ],

 "suggestions":[

 ]
}
```

------

# 4.6 自动返工优化

当评测未通过：

进入优化流程。

流程：

```
Evaluator

↓

发现问题

↓

Refiner Agent

↓

修改内容

↓

重新评测
```

Refiner Agent 根据：

- 原始内容；
- 评测结果；
- 修改建议；

生成优化版本。

------

# 4.7 Human-in-the-loop

为了提高系统可靠性，引入人工反馈机制。

## 场景1：用户主动修改

用户：

```
第三章减少技术细节，
增加商业应用案例
```

系统：

重新调整相关内容。

------

## 场景2：自动优化失败

例如：

连续优化：

```
生成

↓

评测

↓

优化

↓

评测

↓

优化
```

超过最大次数。

系统停止自动循环，并在内容工作台提示用户继续直接编辑、通过聊天修改或接受当前版本；不跳转到单独的质量检查页面。

------

## 场景3：内容工作台确认

用户在内容工作台可以：

- 接受结果；
- 修改建议；
- 指定重新生成范围。

确认当前正文后进入最终结果页。以上操作均发生在内容工作台，不新增“人工审核”或“质量检查”页面。

------

# 4.8 多模型服务与工厂模式

首期支持四款模型：

- DeepSeek Flash；
- DeepSeek Pro；
- GLM-4.7-Flash；
- GLM-5.3-Flash。

模型接入采用统一接口和工厂模式：

```text
LangGraph 节点

↓

Model Router

↓

LLMServiceFactory

↓

DeepSeekService / GLMService

↓

对应厂商 API
```

- `Model Router` 根据任务复杂度、用户首选和节点策略选择具体模型；
- `LLMServiceFactory` 根据模型目录中的 provider 返回对应 service；
- `DeepSeekService` 实现 DeepSeek Flash 与 DeepSeek Pro 的请求、响应、错误和 usage 解析；
- `GLMService` 实现 GLM-4.7-Flash 与 GLM-5.3-Flash 的请求、响应、错误和 usage 解析；
- 工作流节点只依赖统一 `LLMService`，不得直接调用厂商 SDK；
- 显示名称、API 模型 ID、base URL、超时、能力档位、节点映射和备用链放在独立的非敏感模型配置文件中；
- `.env` 只保存 `DEEPSEEK_API_KEY`、`GLM_API_KEY` 等密钥类敏感数据，`.env.example` 不写真实值。

# 4.9 Token 消耗统计

系统应记录每一次实际发出的模型或 Embedding API 调用，并按任务汇总 Token 消耗。

单次调用至少记录：

- 任务 ID、节点、调用用途；
- provider、实际模型和尝试序号；
- 输入 Token、输出 Token、总 Token；
- 供应商返回时的缓存 Token 和推理 Token；
- 重试、降级、结果状态和 provider request ID；
- usage 是否完整。

任务汇总必须包含需求解析、大纲生成、Embedding、内容生成、后台质量评估、自动修订和聊天修改产生的实际调用。重试和降级各自计量；未返回 usage 的调用标记为不可用，不得按 0 处理。后端通过 `GET /tasks/{taskId}/token-usage` 返回总量、按模型/节点汇总和调用明细。

负责：

内容生成。

------

负责：

------

## 5.7 Refiner Agent

负责：

根据反馈优化内容。

------

## 5.8 模型基础组件

- Model Router：选择实际模型并处理配置化降级；
- LLMServiceFactory：根据 provider 创建模型 service；
- DeepSeekService：承载 DeepSeek 厂商具体调用；
- GLMService：承载 GLM 厂商具体调用；
- Token Usage Recorder：保存调用级 usage 并维护任务级汇总。

这些组件不是业务 Agent。Agent 不得自行拼接厂商地址、读取具体密钥变量或实现 Token 累加逻辑。

# 6. LangGraph工作流设计

核心流程：

```text
用户输入需求 + 上传文件

↓

文件解析/索引 + Requirement Agent

↓

Planner Agent 使用需求和上传资料生成大纲

↓

用户直接编辑/聊天修改并确认大纲

↓

Research Agent 检索资料 + Writer Agent 生成内容

↓

用户直接编辑/聊天修改内容

↓

后台 Evaluator Agent

├─ PASS：保留当前内容

└─ FAIL 且未达上限：Refiner Agent → Writer Agent → Evaluator Agent

↓

用户确认正文

↓

最终结果展示 + Markdown 下载
```

后台评估失败且达到修订上限时，流程回到内容工作台并提示用户继续修改或确认当前版本，不创建独立的质量检查步骤。

# 12. 最终项目效果

用户：

```
生成一份关于大模型发展的15页技术汇报，
参考上传的行业报告。
```

用户与系统按以下路径协作：

1. 用户输入需求并上传行业报告；
2. 系统解析资料，并利用需求和资料生成大纲；
3. 用户直接编辑或通过聊天修改大纲，然后确认；
4. 系统按页面目标检索资料并生成正文；
5. 后台 Agent 自主评估并在上限内自动修订；
6. 用户直接编辑或通过聊天修改正文，然后确认；
7. 系统展示最终结果并提供 Markdown 复制和下载；
8. 用户可查看本任务的 Token 汇总和调用明细。
