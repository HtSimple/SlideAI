# SlideAI 首期 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task by task. Each task uses TDD and ends with a verified commit.

**Goal:** Build the complete local, single-user SlideAI v1 from engineering skeleton through hardening, meeting AC-01–AC-28, including four-model Factory/service routing, per-task Token usage and the four-stage user flow.

**Architecture:** A layered FastAPI modular monolith with a separate Celery worker; PostgreSQL stores business projections and LangGraph checkpoints, Redis brokers and coordinates, Chroma stores task-filtered vectors, and a local shared volume stores source files. Vue 3 consumes `/api/v1` through a generated/centralized typed Axios client.

**Tech Stack:** Python 3.12, uv, FastAPI, Pydantic v2, SQLAlchemy async, Alembic, LangGraph, LangChain, Celery, PostgreSQL 16+, Redis, Chroma; Vue 3, TypeScript strict, Vite, Pinia, TanStack Vue Query, Element Plus, Axios, Vitest, Playwright, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-09-28-slideai-v1-design.md`; binding source documents are `docs/需求分析.md`, `docs/开发指导.md`, and `docs/前端设计.md`.

## Global Constraints

- Follow implementation phases 0–7 in `docs/开发指导.md`; each phase must run and be testable before the next phase.
- Keep Pydantic validation between every LLM response and business state; use Fake service implementations in CI and never require real credentials in CI.
- Scope every task-owned read/write to `task_id`; never query broadly and filter in application memory.
- Keep API routes thin; place business policy in application/domain services and workflow nodes.
- Keep Python 3.12 and TypeScript strict; no credentials, real user files, prompts, or unredacted secrets in logs/repository.
- Run every project service, dependency install, migration, lint, type check, test, browser test, and build inside Docker Compose containers; the host only needs Docker Engine and Compose, not Python/uv, Node/pnpm, PostgreSQL, Redis, or Chroma.
- Preserve API paths, stable error codes, version checks, default limits, model retry/fallback rules, and the five-page frontend information architecture from the spec.
- Keep the user path fixed as requirements/files → editable/chat-enabled outline → retrieval plus editable/chat-enabled content → final Markdown result; evaluation/refinement stays an internal Agent loop.
- Store only API Key class secrets in `.env`; keep model IDs, base URLs, timeouts, tiers, node mappings and fallback chains in versioned non-sensitive configuration.
- Use TDD for behavior; each test must be observed failing for the intended reason before production code is written.

## Review Focus

- Cross-task ID substitution or missing tenant filter must return not-found/authorization-safe behavior; pin in repository/API tests.
- Crash between database commit and Celery publish must not lose or duplicate work; pin with outbox retry/idempotency integration tests.
- Malicious filenames, MIME/signature mismatch, oversized/decompression-heavy documents must be rejected without writing outside storage root; pin parser/storage tests.
- Model outputs containing invalid JSON, unknown citation IDs, or prompt-injection text must not corrupt state or trigger tools/network calls; pin service/workflow tests.
- Duplicate delivery or retry must not double-count Token usage; missing provider usage must mark the task summary incomplete instead of recording zero; pin usage repository/API tests.
- Resume after interruption or worker restart must not repeat non-idempotent side effects or overwrite a newer task version; pin checkpoint/version tests.
