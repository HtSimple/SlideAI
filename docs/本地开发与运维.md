# SlideAI 本地开发与运维

## 运行边界

应用及其工具链均通过 Docker Compose 运行：Python 3.12、Node.js/pnpm、FastAPI、Celery、PostgreSQL、Redis、Chroma 和 Playwright 都在容器内。宿主机只需要 Docker Engine 与 Docker Compose，并提供代码目录和 Docker 端口映射；不需要安装本项目的 Python、Node.js、数据库或向量库。

Compose 默认将 Web、API 绑定到本机回环地址 `localhost:4173` 和 `localhost:8000`。可通过 `HOST_BIND_ADDRESS`、`FRONTEND_HOST_PORT`、`API_HOST_PORT` 调整宿主机监听地址和端口，容器间仍使用 Compose 服务名通信。当前版本是本地单用户/受信网络部署，不带登录认证，不要直接暴露到公网。

## 首次启动

在仓库根目录使用 PowerShell：

```powershell
Copy-Item .env.example .env
```

演示模式使用 fake 文本模型和 fake embedding，不需要密钥。需要调用真实模型时，在 `.env` 中配置 OpenAI-compatible 服务地址、模型 ID 和密钥；生成模型与 Embedding 模型的配置彼此独立。不要把 `.env` 或真实密钥提交到 Git。

构建镜像、启动数据库依赖并执行空库迁移：

```powershell
docker compose build
docker compose up -d postgres redis chroma
docker compose run --rm api uv run --frozen alembic upgrade head
docker compose up -d --build
docker compose ps
```

Compose 将 `api`、`worker`、`frontend`、`postgres`、`redis` 和 `chroma` 纳入健康检查。验证 API 与界面：

```powershell
$apiPort = (docker compose port api 8000).Split(":")[-1].Trim()
$frontendPort = (docker compose port frontend 4173).Split(":")[-1].Trim()
Invoke-RestMethod "http://localhost:$apiPort/health/live"
Invoke-RestMethod "http://localhost:$apiPort/health/ready"
Write-Output "Frontend: http://localhost:$frontendPort"
Write-Output "OpenAPI: http://localhost:$apiPort/docs"
```

默认打开 [http://localhost:4173](http://localhost:4173)，OpenAPI 页面位于 [http://localhost:8000/docs](http://localhost:8000/docs)。上面的 `docker compose port` 会按当前 `.env` 端口覆盖解析实际宿主机端口；容器内健康检查仍使用固定的服务端口。Worker 以 Celery worker + beat 运行；beat 会定期发布 PostgreSQL transactional outbox 中的待处理事件。

## 配置

`.env.example` 是完整默认配置清单。最常调整的项：

| 配置 | 默认值 | 用途 |
| --- | --- | --- |
| `HOST_BIND_ADDRESS`、`API_HOST_PORT`、`FRONTEND_HOST_PORT` | `127.0.0.1`、`8000`、`4173` | 调整宿主机绑定地址和端口；默认仅监听回环接口 |
| `GENERATION_PROVIDER` | `openai_compatible` | 演示可设为 `fake`；真实模型使用兼容接口 |
| `GLM_BASE_URL`、`GLM_MODEL_ID`、`GLM_API_KEY` | 空 | GLM 首选模型 |
| `DEEPSEEK_BASE_URL`、`DEEPSEEK_FLASH_MODEL_ID`、`DEEPSEEK_PRO_MODEL_ID`、`DEEPSEEK_API_KEY` | 空 | DeepSeek 模型及备用链 |
| `EMBEDDING_PROVIDER` | `fake` | Embedding 服务与生成服务分开配置 |
| `EMBEDDING_BASE_URL`、`EMBEDDING_MODEL_ID`、`EMBEDDING_API_KEY` | 空 | OpenAI-compatible Embedding 接口 |
| `CORS_ORIGINS` | `http://localhost:4173` | 逗号分隔的精确允许来源，不支持通配符 |
| `MAX_AUTO_REVISIONS` | `2` | 自动修订上限 |
| `EVALUATION_PASS_SCORE` | `85` | 评估通过分数 |
| `MAX_FILE_SIZE_BYTES`、`MAX_FILES_PER_TASK` | `20971520`、`10` | 上传大小和数量上限 |
| `CHUNK_SIZE_TOKENS`、`CHUNK_OVERLAP_TOKENS`、`RETRIEVAL_TOP_K` | `800`、`120`、`6` | 文档分块及检索设置 |
| `MODEL_RETRY_COUNT`、`WORKFLOW_LOCK_TTL_SECONDS` | `2`、`60` | 模型重试及工作流锁 |

修改环境变量后重建/重启受影响的容器：

```powershell
docker compose up -d --force-recreate api worker
```

若修改宿主机端口映射，请同时重建前端/API 容器：

```powershell
docker compose up -d --force-recreate api worker frontend
```

## 常用开发与质量命令

命令均在容器中执行；`--no-deps` 仅用于不需要数据库、Redis 或 Chroma 的静态检查和单元测试。

```powershell
docker compose run --rm --no-deps api uv run --frozen ruff format --check .
docker compose run --rm --no-deps api uv run --frozen ruff check .
docker compose run --rm --no-deps api uv run --frozen pyright
docker compose run --rm --no-deps api uv run --frozen pytest -q
docker compose run --rm -e RUN_INTEGRATION_TESTS=1 api uv run --frozen pytest -q tests/integration
docker compose run --rm --no-deps frontend pnpm lint
docker compose run --rm --no-deps frontend pnpm type-check
docker compose run --rm --no-deps frontend pnpm test --run
docker compose run --rm --no-deps frontend pnpm format:check
docker compose run --rm --no-deps frontend pnpm build
docker compose -f docker-compose.yml -f docker-compose.e2e.yml --profile test run --rm e2e pnpm test
```

建立隔离空库可使用独立 Compose 项目名，避免触碰日常开发数据：

```powershell
docker compose -p slideai-empty up -d postgres redis chroma
docker compose -p slideai-empty run --rm api uv run --frozen alembic upgrade head
docker compose -p slideai-empty down -v
```

最后一条仅删除 `slideai-empty` 这个隔离项目新建的容器和卷；不要对日常项目执行 `down -v`，除非明确要销毁其中的数据。

## 数据、备份与恢复

PostgreSQL 持久化任务、来源文本/分块元数据、修订、聊天、模型调用审计、checkpoint 和 outbox。上传文件保存在 `slideai_files` 卷；向量保存在 Chroma 的 `chroma_data` 卷。仅备份 PostgreSQL 并不足以完整恢复资料检索，三个部分应在应用和 Worker 停止写入后一起备份。

以下 PowerShell 示例将 PostgreSQL 逻辑备份和应用文件复制到仓库外的安全位置；请按 `.env` 中自定义的数据库名/用户修改参数，并妥善保护备份文件：

```powershell
docker compose stop api worker frontend
docker compose exec -T postgres pg_dump -U slideai -Fc -d slideai -f /tmp/slideai.dump
$api = docker compose ps -q api
$chroma = docker compose ps -aq chroma
docker compose exec -T api tar -czf /tmp/slideai-files.tar.gz -C /var/lib/slideai/files .
$postgres = docker compose ps -q postgres
docker compose stop chroma
docker cp "${postgres}:/tmp/slideai.dump" .\slideai.dump
docker cp "${api}:/tmp/slideai-files.tar.gz" .\slideai-files.tar.gz
docker cp "${chroma}:/chroma/chroma" .\slideai-chroma
docker compose start chroma api worker frontend
```

恢复前先停止 API、Worker 和前端，并将文件复制回原卷。数据库恢复会覆盖现有 schema 数据：

```powershell
docker compose stop api worker frontend chroma
$postgres = docker compose ps -q postgres
$api = docker compose ps -aq api
$chroma = docker compose ps -aq chroma
docker cp .\slideai.dump "${postgres}:/tmp/slideai.dump"
docker cp .\slideai-files.tar.gz "${api}:/tmp/slideai-files.tar.gz"
docker compose exec -T api sh -c 'find /var/lib/slideai/files -mindepth 1 -delete && tar -xzf /tmp/slideai-files.tar.gz -C /var/lib/slideai/files'
docker compose exec -T chroma sh -c 'rm -rf /chroma/chroma'
docker cp .\slideai-chroma "${chroma}:/chroma/chroma"
docker compose exec -T postgres pg_restore --clean --if-exists --no-owner -U slideai -d slideai /tmp/slideai.dump
docker compose start chroma api worker frontend
```

恢复后查看健康状态和日志，并从任务中心检查任务与文件。建议定期在隔离环境演练恢复；当前仓库不包含自动备份调度、异地存储或备份加密设施。

## 常见维护操作

```powershell
docker compose logs --tail 200 api worker
docker compose logs -f worker
docker compose ps
docker compose run --rm api uv run --frozen alembic current
docker compose run --rm api uv run --frozen alembic upgrade head
docker compose restart worker
```

任务数据默认持续保留到用户删除。删除只接受 DRAFT/READY 任务，并先以版本更新占用删除操作，防止与启动竞态；文件和向量清理失败时保留 `CANCELLED/deletion_requested` 状态，可再次调用删除重试。运行中任务可取消；Worker 在获得任务锁后校验 outbox 事件，并以 Redis 持久化的单调租约代数登记当前 Worker。进度、页面批次、修订、LangGraph checkpoint、状态投影和失败标记都在数据库行锁下校验租约代数，锁过期后的旧 Worker 不能覆盖新 Worker 的结果。有效事件遇到锁忙或 PostgreSQL/Redis 暂时不可用时，Celery 会退避重试；过期事件会被丢弃。日志不会包含 API 密钥、提示词、上传文档正文或异常堆栈内容。

## 当前限制

- 无登录、权限、租户、速率限制或恶意文件扫描；仅供本地或受信网络。
- 只生成结构化文字和 Markdown；不生成 PPTX、不做视觉排版，也不联网搜索。
- 真实模型调用需要用户自行配置兼容服务及凭证。CI 和默认测试使用 Fake provider；真实厂商 endpoint/密钥的 smoke test 不属于阻塞检查。
- Docker 挂载开发源文件会触发热重载；生产部署应改为不可变镜像和独立密钥管理，并另行评估备份、TLS、认证、限额和公网安全。
